## Methodology (the loop that works — proven on the UK-gov cluster)
For each adapter cluster AND each pipeline stage:
1. **PROBE the real wired path live** — `extract → prepare_query → search → pool` on representative claims (`scripts/probe_prepare_query.py` pattern). Never reason from static code or stale docs alone.
2. **DIAGNOSE should-vs-is** — what should this return for the very best result, vs what it does, vs *why*.
3. **FIX mechanically** — never prompt-only ([[feedback_nf11_prompt_only_failed]]).
4. **VERIFY** — unit tests + `/verify-implementation` (G5) + replay bench + live yield.
5. **COMMIT per cluster** (rollback unit). Update this register.

**Why this section exists:** NF-19 (`a903729`) fixed a state-correctness bug (incomplete supports/challenges census → wrong element state, e.g. supported→disputed). The handoff flagged a follow-up: the bench does not assert state correctness, so NF-19 is not regression-detectable.

**⚠️ CORRECTION 2026-06-17 (fresh telemetry refuted an earlier read of stale telemetry).** Initial research concluded `[B3 RECEIPTS] shown=0` had killed the whole per-claim V3 gate. That was **based on a stale `observation.json` captured at `9231994` — the commit BEFORE NF-19** (B4A3 golden `captured_with: 9231994`). A fresh live re-record at current HEAD (`a903729` + uncommitted bench work) shows the opposite: **`b3_receipts={shown:55, unmapped:3}`, refs match `evidence_id` 100% on all 3 claims, `b3_quality_per_claim` populated, `element_resolution=1.0`.** **NF-19's always-run census backstop (gate 3→1) references ~all evidence → receipts tag them `shown` → the V3 gate is LIVE.** So `shown=0` and the "dormant V3 gate" cascade were a **pre-NF-19 artifact, already resolved**. No receipt-data fix (former L1) is needed. Lesson logged: a golden/observation predating a fix is not HEAD truth — re-record before concluding ([[feedback_knowledge_loop]]).

**Net after correction:** the alarming part (shown=0 / dormant gate) was stale-data; **already fixed by NF-19.** The genuine, still-valid work is making NF-19 **regression-detectable**: L3 state-correctness signal + L4 census diagnostic, plus a b3-counter guard. Design: `audit/2026-06-17_mapping_completeness_design.md`.

**⏸️ THREAD PAUSED 2026-06-17 (positioning/orientation reframe takes priority).** Implementation reached: L3/L4 signals + receipt regression guard + dump tooling all built and unit-tested (71 green); corpus re-recorded at HEAD. **But wiring an exact `[ELEMENT STATE]` assertion exposed a foundational blocker (new row below) + a date-norm mis-step, so the bench could not be made green deterministically.** Code reverted to the proven-green baseline; the full design + findings live in the design doc for resumption. **No live-site bug** — the replay "collapse" is a cassette-miss → fallback artifact, not production behaviour (inherent LLM/search variance; convergence layer already addresses run-to-run). The deterministic NF-19 guard, when resumed, belongs at the **unit level** (frozen-fixture state assertion), not the replay bench.

**State derivation (the thing a correctness guard protects) — fully mapped:** `_derive_element_state_with_authority` (`claim_map_analyzer.py:517`) is a mechanical tier-weighted count over `evidence_refs` (primary=3/reporting=2/commentary=1). Rules: all-supports→supported, all-challenges→disputed, ≥2× weighted→that side, **close_split→disputed** (`:615-617` — the NF-19 signature: a 1-support/1-challenge *sample* lands disputed; a complete 10/1 census → `supports_dominant_2x`→supported). The rule is CORRECT; correctness is entirely a function of census completeness. The `state_basis` dict it emits (`:653-661`) already holds `supports_count/challenges_count/weighted_*/rule_applied/llm_state` — everything a signal needs, already persisted to `elem["basis"]["state_derivation"]`.

**Proposed signal design (settled, evidence-backed):**
1. **PREREQUISITE — fix shown=0 receipt-data divergence** (else b3_quality stays empty and receipts-based signals are dead).
2. **State-correctness regression guard (highest leverage):** new always-on `[ELEMENT STATE]` line → capture → golden records expected per-element `(state, rule)` → comparator FAILs on a state flip or a rule regression (e.g. `all_supports → close_split` = census shrank). This is the ONLY shape that would have caught NF-19.
3. **Census-completeness diagnostic:** capture `[MAP COMPLETION]`; band-assert `still_unmapped` on rich-pool claims.
4. Keep `mapped` rate DIAGNOSTIC-only (V3 philosophy — low rate + high-quality mapped set is still fine). Completeness ≠ rate.

**Inefficiency noted:** the NF-19 census backstop (`_complete_unmapped_evidence`) now runs on EVERY claim with ≥1 leftover (gate dropped 3→1) — one extra Flash-Lite call/claim (~$0.001 + latency; up to 5/check). Deliberate cost-for-correctness trade, documented; a future optimisation could skip the LLM call when the census is already trivially complete.
